# Спека: механизм интеграций

Контекст: контент сторонних модов подключается через сервисный реестр (`IntegrationServices`,
DI-подобный). Ядро резолвит реализации сервисных контрактов (`GetServices<T>()`); интеграция —
это отдельный проект `AnimalSlaughterManager.Integrations.<Mod>` со ссылкой на Core (обёртка
чужого API, сервисы по контрактам, свои модели/правила/UI, README). Регистрация происходит в
статическом конструкторе класса с атрибутом `[StaticConstructorOnStartup]` внутри интеграции —
RimWorld запускает все такие классы при загрузке игры; тот же атрибут в своём моде может
использовать и любой сторонний мод, чтобы зарегистрировать интеграцию (себя или третьего
мода) с этим модом.

## Сценарии

### Спека 1: под контракт ничего не зарегистрировано

```gherkin
Rule: Пустой реестр
  Given под контракт не зарегистрировано ни одной реализации
  When ядро вызывает GetServices<T>()
  Then возвращается пустой список — ядро работает как без интеграций
```

### Спека 2: регистрация при старте

```gherkin
Rule: Регистрация
  Given чужой мод активен
  When игра загружается и отрабатывает [StaticConstructorOnStartup] интеграции
  Then каждый сервис интеграции зарегистрирован под свой контракт (Add<T>)
  And ядро резолвит его через GetServices<T>() вместе с остальными
```

### Спека 3: несколько реализаций одного контракта

```gherkin
Rule: Композиция
  Given под контракт зарегистрированы две реализации
  When ядро резолвит контракт
  Then обе участвуют: суммы складываются, списки объединяются,
    одиночные вопросы истинны, если хоть одна реализация отвечает истинно
```

### Спека 4: настройки вида переживают выключение чужого мода

```gherkin
Rule: Хранение настроек
  Given в настройках вида есть данные интеграции
  When чужой мод выключен и сейв загружен
  Then провайдер настроек зарегистрирован (безусловно) и данные читаются/сохраняются
  And применяются при повторном включении
```

### Спека 5: новая интеграция не меняет ядро

```gherkin
Rule: Точка расширения
  Given появляется новый источник контента, укладывающийся в существующие контракты
  When для него создаётся проект интеграции с сервисами и классом саморегистрации
  Then ядро не меняется вовсе
```

## Инварианты

- Реестр — единственная точка расширения; ядро использует только контракты.
- Контракт — по точке потребления ядра и лежит в `.Shared/` этой фичи; интеграционно-специфичные
  запросы (перечисление дефов, проверки черты у пешки) в контракты не входят — они остаются
  внутри интеграции, в её обёртке чужого API.
- Поведение каждой точки потребления при любом числе реализаций определено в самой точке
  (сумма/объединение/любая) и описывается спекой этой точки.
- Хранение данных интеграции: в настройках вида — по ключу провайдера; в пресетах — своя
  XML-секция (легаси-форматы читаются самой интеграцией).
